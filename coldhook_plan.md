# ColdHook — статический инлайн-патчер + инжектор + ресайн

«Холодный» хук: без рантайм-кодогенерации, без JIT, без debugged-режима.

Цель: переиспользуемый инструмент, который по таблице `{addr → замена}` вписывает
трамплины/венири прямо в Mach-O, опционально добавляет рантайм-dylib + load command,
и переподписывает. Без рантайм-кодогенерации → **не упирается в W^X** (страницы `__TEXT`
остаются RX и покрыты подписью с этапа сборки; ни одного перехода RW→RX в рантайме).

## Pipeline

```
IPA/Mach-O ─► parse ─► [hook table] ─► add section ─► gen veneers ─►
   ─► patch sites ─► (opt) add LC_LOAD_DYLIB ─► fix codesign slots ─► re-sign ─► repack IPA
```

Вход — таблица хуков:

```python
HOOKS = {
  0xb99a8:  Replace(export="my_url_for"),     # full replace
  0x16ae8c: Detour(export="my_bundle_env"),    # inline, с возвратом в оригинал
}
```

## Фаза 0 — каркас и парсинг

- CLI: `coldhook patch <ipa|macho> --hooks hooks.py --dylib libhook.dylib --cert <id>`.
- Распаковка IPA → найти главный бинарь / нужный framework (по имени модуля).
- Парсинг через **LIEF**: сегменты, секции, `__TEXT`, entry, load commands.
- Детект arch (arm64), проверка cryptid (== 0, decrypted).
- Выхлоп: объект `Target` с доступом к байтам по виртуальному адресу.

## Фаза 1 — место под код (code cave / новая секция)

- Стратегия А: добавить новую секцию в `__TEXT` (`__hook`) через LIEF — туда венири.
- Стратегия Б: найти существующий code cave (паддинг в хвосте `__TEXT`).
- Проверить, что секция в **±128 МБ** от сайтов (для прямого `B`), иначе дальний венир.
- Выхлоп: аллокатор `alloc(n) -> vaddr` в зоне хуков.

## Фаза 2 — генерация венниров/трамплинов (arm64)

**Replace (перенаправить вызов):**
```asm
; на сайте:  B  veneer
; veneer:
LDR  X16, #8
BR   X16
.quad <addr замены>          ; экспорт в этом же бинаре или в dylib
```

**Detour (инлайн-хук с возвратом в оригинал):**
1. сохранить N инструкций пролога цели (с релокацией PC-relative!)
2. trampoline = [relocated пролог] + [LDR X16/BR X16 → original+N]
3. на цель: `B → hook`; hook по завершении прыгает в trampoline

- Самое хитрое — релокация ADRP/ADR/LDR-literal/B/BL при переносе → модуль `reloc_arm64`.
- X16/X17 (IP0/IP1) — caller-saved, можно кробить на границе вызова.

## Фаза 3 — патч сайтов

- Записать `B imm26` (или `BL`, если нужен возврат адреса) на каждом target_addr.
- Проверка дальности (±128 МБ); если не лезет — двухступенчатый прыжок через ближний венир.
- Выравнивание 4 байта; учесть начало функции vs середина.

## Фаза 4 — резолв замен (где хостить код)

- **В том же бинаре** (добавленная секция): нет dylib, self-contained. Минус — замену писать
  готовым arm64 или линковать свой `.o` в секцию.
- **В отдельном dylib**: добавить `LC_LOAD_DYLIB @executable_path/Frameworks/libhook.dylib`,
  резолв экспорта через символ; венир грузит указатель из GOT (его заполнит dyld). Гибче,
  Swift String строить проще.

## Фаза 5 — Swift-возвраты (отдельная боль)

- Вернуть валидный Swift `String`/enum — Swift calling convention + ARC + String representation.
- Решение: замену писать на Swift в dylib с совместимой сигнатурой, венир передаёт управление.
- Смэтчить mangled-сигнатуру цели → объявить совместимую замену.

## Порядок сборки (милстоны)

1. **M1:** parse + add section + один захардкоженный Replace-венир + ресайн → ставится, не падает.
2. **M2:** hook-таблица + дальний венир + патч N сайтов.
3. **M3:** Detour-режим с релокацией пролога (трамплин-возврат).
4. **M4:** dylib-хостинг + GOT-резолв + Swift-замена с корректным String.
5. **M5:** обёртка IPA-in/IPA-out, CLI, конфиг.

## Риски / решить заранее

- Релокация ADRP/LDR-literal при переносе пролога — главный технический риск.
- Дальность венниров (новая секция в радиусе ±128 МБ).
- Корректность `__LINKEDIT`/codesign после LIEF (иногда проще пересобрать слепок подписи целиком).
- Сломанные при правке: `LC_CODE_SIGNATURE`, `LC_FUNCTION_STARTS`, `DATA_IN_CODE` — починить/пересоздать.
- Anti-tamper банка (проверка хеша секций) может детектить и статику.

## Prior art: MachOMerger (Dopamine / opa334)

https://github.com/opa334/Dopamine/tree/2.x/BaseBin/MachOMerger/Sources/MachOMerger
(использование: `BaseBin/dyldhook/src/spinlock_fix.c` через макросы `HOOK()`/`ORIG()`)

**Боевой прообраз ColdHook, но мощнее.** Это не «вставь венир в секцию», а **полное
слияние двух Mach-O в один**: скомпилированный хук-бинарь (patch) сливается с целевым
(target) на этапе сборки. Написан на Swift.

Что решает «по-взрослому»:
- слияние сегментов по имени (r-x / r-- / rw-), релокация всего на новые vmaddr с `0x4000`;
- **chained fixups merge** (`mergeChainedFixups`) + split info (`fixupViaSplitInfo`) +
  символы — честно пересобирает rebase/bind-цепочки обоих бинарей (это наш главный риск,
  тут уже закрыт);
- magic-символы как механизм хука (резолвятся при слиянии в патчи веток):
  - `_MACHOMERGER_HOOK_<fn>` — патчит цель веткой на хук, оригинальную первую инструкцию
    сохраняет в `_MACHOMERGER_ORIG_<fn>` (= наш Detour-режим с возвратом);
  - `_MACHOMERGER_TRAMPOLINE_*` / `_HOOKTRAMPOLINE_*` — прямые ветки;
  - `_MACHOMERGER_REAL_START` — оригинальный entry (`__pc`) из UnixThread;
- кодировка ветки: `0x14000000 | delta` (`B`), проверка `"Delta too large!"` (26 бит).

**Ключевой архитектурный вывод:** раз он сливает всё в один бинарь и релоцирует оба в
общее адресное пространство — хук-код оказывается рядом с целью, и `B` всегда дотягивается.
**Дальние венири (`LDR X16/BR X16`) не нужны вообще** — проблема снята архитектурно.

Что это меняет в плане ColdHook — две самые больные фазы закрываются мёрджем:

| Боль в ColdHook | Решение MachOMerger |
|---|---|
| Фаза 4: где хостить замену | сливаешь целый скомпилированный хук-бинарь → пишешь на C/Swift |
| Фаза 5: вернуть валидный Swift String | обычный Swift-код в хук-бинаре, не руками |
| Релокация пролога / дальность ветки | мёрдж релоцирует всё; branch в радиусе; ORIG хранит оригинал |
| Chained fixups после правки | `mergeChainedFixups` уже умеет |

Чего НЕ хватает под наш кейс (sideload, не JB):
- таргет MachOMerger — **arm64e** (dyld); у нас приложение **arm64** → проверить корректность
  мёрджа/формата chained fixups для arm64;
- **нет переподписи** (в JB не нужна) → прикрутить `codesign`/`ldid`/`applesign` + repack IPA
  после слияния (`__LINKEDIT`/UUID он уже пересобирает, место под подпись чистое);
- заточен под главный бинарь / dyld → прогнать на framework внутри `.app`
  (ModuleA/ModuleB).

**Решение для ColdHook:** строить не как «венир-инжектор», а как **форк/обёртку поверх
merge-подхода**:
1. хуки пишешь обычным Swift/C с magic-символами `_HOOK_`/`_ORIG_`;
2. MachOMerger сливает хук-бинарь в ModuleA/ModuleB;
3. добавляешь шаг codesign/ldid + repack IPA — то, чего у него нет.

Это снимает ~70% риска из плана выше (фазы 2/3/4/5 и пункт про chained fixups).
Архитектура «merge» > архитектура «patch-in-place + section».

## ColdHook ↔ Theos backend (future)

Идея: пишешь твик **обычным Logos-синтаксисом** (`%hookf` / `%orig`), а под капотом вместо
runtime-substrate ColdHook делает **статический merge**. Тот же `.xm` → на выходе статически
пропатченный подписанный IPA (без substrate, без W^X, sideload-friendly).

**Почему ложится:** Logos — это препроцессор-кодген (`logos.pl`), который разворачивает
директивы в C/ObjC с вызовами `MSHookFunction` в конструкторе. MachOMerger делает ту же
связку, но через magic-символы на этапе слияния. Изоморфизм:

| Logos (runtime) | MachOMerger (static) |
|---|---|
| замена `_logos_function$...` | `_MACHOMERGER_HOOK_<sym>` |
| оригинал `_logos_orig$...` | `_MACHOMERGER_ORIG_<sym>` |
| `MSHookFunction(...)` в `%ctor` | не нужен — связывает merge на сборке |

Интеграция = **новый бэкенд кодгена для Logos** (тот же парсер, другой эмиттер:
magic-символы вместо substrate-вызовов). Исходник твика не меняется.

### Тиры сложности

- **Tier 1 — `%hookf` (C + Swift по символу): легко, и это наш основной кейс.**
  Алиаснуть замену на `_MACHOMERGER_HOOK_<mangled>` (через `__asm__`-label), `_ORIG_` как
  extern, `%orig` → вызов через него, убрать ctor. Все Swift-хуки (`url(for:)`,
  `bundleEnvironment(in:)`) — это `%hookf` по mangled-имени.
- **Tier 2 — by-offset: своя директива** (`%hooka(ret, "ModuleA", 0xb99a8)`). MachOMerger
  хукает по символу → нужно доинъектить синтетический символ по адресу перед merge ЛИБО
  расширить merger на адресные хук-записи. Средняя работа.
- **Tier 3 — `%hook` (ObjC по селектору): отдельный проект.** Статического merge-аналога нет,
  но ObjC-метаданные лежат в бинаре (`__objc_const`/methlist), `imp` — указатель
  (rebase/chained-fixup). → **статический свизл**: найти class→method→слот `imp`, переставить
  через fixup-цепочку; `%orig` = исходный IMP. Самостоятельная фича поверх merger.

**Бонус:** `%ctor` может выжить — `__mod_init_func` из хук-dylib смёрджится и отработает при
загрузке. Не мэпится статически: `%new`, `MSHookIvar`, динамические `%group`.

### Точки форка в Theos

1. **`logos.pl` — режим бэкенда** (`LOGOS_BACKEND=coldhook`): тот же парсер, другой эмиттер.
2. **Make-правило / новый тип пакета** в `$(THEOS)/makefiles/` (`coldhook.mk`): `make package`
   вместо `.deb` гонит pipeline compile → MachOMerger merge → resign → repack IPA.

```makefile
TWEAK_NAME = ExampleTweak
ExampleTweak_FILES = Tweak.xm
THEOS_PACKAGE_SCHEME = coldhook          # ← вся разница
COLDHOOK_TARGET = Frameworks/ModuleA.framework/ModuleA
```

### Прагматичный путь

Не форкать Logos сразу. **MVP без модификации Theos:** хук на голом C с `__asm__`-лейблами
под magic-символы (руками то, что эмитил бы бэкенд) → merge → проверить на ModuleA.
**Потом** обернуть в Logos-бэкенд + make-правило, когда уже знаешь, какой кодген эмитить.
Сначала доказать pipeline на Tier-1 руками → потом «сахар» в виде Theos-синтаксиса.

## Optional mode: shared dylib (один dylib на всю логику)

Дефолт ColdHook — **merge** (хук-код внутри каждого таргета, self-contained, тише по
anti-tamper). Опциональный режим (`COLDHOOK_MODE=shared`) — **один `libcoldhook.dylib` со
всей логикой**, таргеты получают только тонкий патч. Удобно, когда логики много и она общая
на кучу таргетов.

Define с модулем (модуль обязателен — оффсет валиден только в контексте бинаря):
```c
// в libcoldhook.dylib
COLDHOOK_HOOK("ModuleA",    0xb99a8,  my_url_handler)
COLDHOOK_HOOK("ModuleB", 0x16ae8c, my_env_handler)
```
ColdHook группирует по модулю и под каждый таргет генерит патч, мапящий
`(module, offset) → указатель на хендлер в dylib`.

### Трудность — не дальность, а чужой образ

Сайт в таргете и `libcoldhook.dylib` — **разные загруженные образа**; их взаимное
расположение = slide + ASLR, известно только в рантайме. `B`/`BL` (±128 МБ) не подходит —
нет константного адреса. Нужен **косвенный переход через указатель**, заполняемый в рантайме.

### Способ A — статическая инъекция импорта (чистый, но самый трудный)

В каждый таргет: `LC_LOAD_DYLIB` + новый импорт + GOT-слот + bind-запись (dyld пропишет
адрес), веннир `ADRP/LDR X16,[GOT]; BR X16`. Проблема: на iOS это `DYLD_CHAINED_FIXUPS`,
и **добавить новый импорт в цепочку сложнее**, чем merge (синтез новых цепочек, а не
релокация существующих). Самый зубодробительный путь.

### Способ B — гибрид: микро-шим + dlsym (РЕКОМЕНДУЕТСЯ)

Import-таблицы не трогаем. В каждый таргет мёрджится крошечный шим:
1. конструктор (`__mod_init_func`): на загрузке `dlopen(@executable_path/Frameworks/
   libcoldhook.dylib)` + `dlsym` хендлеров → пишет указатели в **RW-таблицу в `__DATA`**;
2. венниры на сайтах: `LDR X16,[table+i]; BR X16` — косвенно через таблицу.

Почему лучше A:
- дальность снята полностью (косвенный `BR`, ASLR пофиг);
- никакой хирургии chained-fixups (таблица — обычные данные; шим/венниры мёрджатся как код);
- W^X не трогаем — рантайм-codegen нет, только `dlsym` (чтение) + запись указателей в данные.

Минусы B: лёгкий `dlsym`-инит на загрузке; ctor должен отработать **до** первого вызова
хукнутой функции (для старт-хуков типа `setProject` — норм). Опц. fallback: ленивый резолв
в венире, если указатель ещё null.

### Trade-offs: merge vs shared dylib

| | merge (дефолт) | shared dylib (опция) |
|---|---|---|
| логика | дублируется в каждый таргет | **одна на всё приложение** |
| footprint в таргете | весь хук-код | только шим + венниры + таблица |
| дальние прыжки | не нужны (один образ) | косвенно через таблицу (решено в B) |
| chained-fixups хирургия | нет | нет (B) / да (A) |
| **детект anti-tamper** | всё в родном образе, тише | +чужой dylib + `dlopen` — заметнее |
| `%orig`/трамплин | per-target | per-target (всё равно) |
| обновление логики | re-merge каждого таргета | пересобрать **один** dylib + resign |

**Вывод:** дефолт — merge (стелс); shared dylib — опция через **способ B**, когда логики
много и общая. Главный минус shared — заметность (лишний dylib + `dlopen`), бьёт по стелсу
против anti-tamper.

### Финальный shared-flow (способ B, зафиксировано)

Загрузку делаем через **dyld**, НЕ через ручной mmap — ручной маппинг подписанного dylib на
неджейле **запрещён AMFI** (mmap PROT_EXEC фейлится, mprotect→exec блокируется, exec-страницы
хешируются против codesign-блоба vnode; вдобавок в обход dyld не применятся fixups/binds и не
отработают инициализаторы). Единственный легальный путь — dlopen/dyld. Требование: libcoldhook
**подписан тем же сертом, что app** (делаем на resign).

```
launch
 └─ dyld грузит таргет (ModuleA) → АВТОМАТИЧЕСКИ зовёт шим-ctor (__mod_init_func):
        h = dlopen("@executable_path/Frameworks/libcoldhook.dylib", RTLD_NOW);
        //         ↑ dlopen УЖЕ прогнал конструкторы libcoldhook (вручную НЕ звать!)
        table[0] = dlsym(h, "coldhook_ModuleA_b99a8");   // символы ищем сами
        table[1] = dlsym(h, ...);
        // проверять dlopen/dlsym на NULL и фейлить ЯВНО (иначе BR по нулю → краш)
 └─ хукнутые сайты: LDR X16,[table+i]; BR X16   (косвенно через RW-таблицу в __DATA)
```

**Критично — конструкторы вызываются САМИ, вручную не звать:**
- конструкторы `libcoldhook` → запускает `dlopen` (часть загрузки);
- шим-ctor в таргете (`__mod_init_func`) → запускает `dyld` при загрузке фреймворка.
Ручной вызов init = manual-mapping-паттерн, который мы выкинули; продублируешь init →
двойные аллокации/регистрации/краши. Наша задача — только **написать тело** шим-ctor'а.

**Про dlopen из фреймворка:** ограничение «extensions/frameworks prohibited from dlopen»
касается в основном app-extensions; код таргета крутится в процессе приложения → ок.
Альтернатива, чтобы вообще не звать dlopen явно: добавить `LC_LOAD_DYLIB` в таргет (лёгкая
вставка load command, без хирургии fixups) → dyld авто-грузит libcoldhook на launch, а в
ctor только `dlsym(RTLD_DEFAULT, ...)` (lookup, не загрузка). Запасной путь, если упрёмся.

**Что НЕ делаем:** ручной mmap + ручной fixup + ручной вызов инициализаторов (manual
mapping) — заблокировано AMFI на неджейле, живёт только на JB.

## Стек инструментов

- **MachOMerger** (opa334) — базовый движок слияния хук-бинаря в таргет (форкаем/оборачиваем).
- **LIEF** — parse / patch / add section / add load command (для разведки + если не merge-путь).
- **keystone** — ассемблировать венири.
- **capstone** — дизасм переносимых инструкций (релокация пролога).
- **ldid / codesign / applesign** — подпись (adhoc под TrollStore / dev-серт).
- **IDA + ida-pro-mcp** — разведка сайтов и сигнатур.

## Контекст (SomeBank, кейс на котором тестируем)

Три краша — намеренные `assertionFailure` при старте (неизвестное окружение/домен):

| модуль | файл:строка | функция | адреса (в .i64) |
|--------|-------------|---------|-----------------|
| ModuleA | `SourceA.swift:37` | `TypeA.makeUrl(for:)` | тело `0xb99a8`, assert `0xb9d48`, brk `0xb9d4c`; вызыв. `ManagerA.configure` `0x127254` |
| ModuleB | `SourceB.swift:33` | `TypeB.environment(in:)` | тело `0x16ae8c`, assert `0x16b1b8`, brk `0x16b1bc`; `fieldB` `0x16ab58`, `TypeB.set` `0x16a6bc` |

Первая боевая цель для M1/M4: перенаправить `TypeA.makeUrl(for:)` (`0xb99a8`) на свою
замену, возвращающую валидный домен-String, вместо провала в assert.
